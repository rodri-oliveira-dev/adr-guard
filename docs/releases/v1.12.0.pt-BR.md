## Destaques

- Adiciona `adr-guard export relationships [diretório]` para exportar metadados de ADRs, relacionamentos declarados e diagnósticos de validação atribuíveis em JSON determinístico.
- Define o contrato portátil de exportação de relacionamentos com `"schemaVersion": "1.0"` e exemplos canônicos em bytes para consumidores externos, incluindo o Align.
- Separa a resolução da identidade do alvo (`resolved`, `ambiguous` ou `unresolved`) da semântica do relacionamento. Um alvo resolvido não comprova que o relacionamento é válido, aprovado ou conforme.

## Comando e saída

```bash
adr-guard export relationships docs/adr
adr-guard export relationships docs/adr --output artifacts/relationships.json
```

A saída padrão é `.adr-guard/relationships.json`. Um `--output` explícito deve ser um caminho JSON portátil dentro do repositório. O artefato contém três arrays ordenados deterministicamente:

- `adrs`: identificador, caminho relativo ao repositório, título e status validado;
- `relationships`: todo relacionamento declarado `supersedes`, `superseded-by` e `depends-on`, incluindo origem, declaração, alvo resolvido quando disponível e classificação da resolução;
- `issues`: diagnósticos atribuíveis do Core com código, severidade, mensagem e caminho relativo ao repositório.

A exportação não inclui timestamps nem estado Git implícito. Conteúdo do repositório e entradas explícitas idênticos produzem bytes idênticos.

## Comportamento dos códigos de saída

- `0`: o artefato foi gravado, inclusive quando `issues` não está vazio;
- `2`: o uso do comando ou a configuração do repositório é inválida;
- `3`: houve falha no carregamento da entrada, na validação de caminho/segurança, no cancelamento ou na E/S da saída.

A exportação é uma operação de integração, não um gate de política. Execute `adr-guard check` separadamente quando findings de validação precisarem controlar a CI; os significados estabelecidos da CLI, `1` para findings e `4` para falha de política determinística, continuam inalterados nos comandos que os utilizam.

## Segurança, portabilidade e confiabilidade

- As entradas são Markdown UTF-8 válido, limitadas a 1.000 ADRs e 524.288 bytes por ADR.
- A descoberta ignora links simbólicos e reparse points. A contenção no repositório rejeita caminhos absolutos, traversal, escapes por links e caminhos que não podem ser representados pelo contrato portátil separado por `/`.
- A escrita cria e descarrega em disco um arquivo temporário no diretório de destino antes de substituir o artefato anterior. Ela não edita ADRs, índices, configuração nem estado Git.
- A exportação não exige rede, modelo, provider ou credencial. Consumidores como o Align podem importar o JSON pronto sem executar ADR Guard, .NET, MCP ou uma integração de IA.
- Saída de IA e uma aresta resolvida permanecem dados consultivos; nenhum deles pode aprovar uma ADR ou estabelecer conformidade.

## Compatibilidade e limitações conhecidas

- O schema `1.0` é aditivo aos contratos existentes da CLI. Sua política de compatibilidade `major.minor` exige nova versão major para mudanças incompatíveis; nenhum schema JSON ou SARIF existente foi alterado.
- Comandos, argumentos, fingerprints de validação, ordenação e contratos de códigos de saída existentes são preservados.
- A exportação relata relacionamentos declarados e diagnósticos de validação atribuíveis. Ela não infere arestas não declaradas, avalia mérito arquitetural, aplica findings nem inspeciona repositórios externos.
- `resolution: "resolved"` significa que exatamente uma identidade de alvo foi encontrada. Ciclos, declarações inversas inconsistentes, dependências inativas, status inválidos e outros findings semânticos permanecem em `issues`.
- O código-fonte MCP atual reutiliza o produtor do Core, mas mapeia os resultados para o contrato MCP schema `1.0` existente e o valor histórico de resolução `valid`. O MCP `1.0.1` não é republicado nem versionado por esta release da CLI.

O workflow coordenado **Release** valida o SemVer estável contra `VersionPrefix`, restaura, compila, testa, empacota, instala e executa smoke tests no commit selecionado da CLI antes da distribuição:

- publicar `RodriOliveira.AdrGuard` `1.12.0` no NuGet.org e GitHub Packages;
- publicar imagens correspondentes `linux/amd64` e `linux/arm64` no GHCR e Docker Hub;
- criar a tag exata `v1.12.0`, mover a tag de compatibilidade `v1` somente depois dos gates de publicação e criar a GitHub Release com estas notas curadas.

A publicação da CLI `1.12.0` ocorreu de forma separada do merge, pelos gates do workflow de release.

## Componentes fora desta release

- `AdrGuard.Core` é interno e não empacotável; ele acompanha o pacote da CLI e não tem versão independente.
- O MCP continua versionado independentemente na versão publicada `1.0.1`, com workflow próprio. A versão do pacote e o manifesto do Registry permanecem inalterados.
- O VS Code `1.1.1` está publicado independentemente no Visual Studio Marketplace; ele não é incluído nem publicado pelo workflow da CLI.
- `AdrGuard.Agent` continua sendo código-fonte de desenvolvimento, sem versão. Ele não possui pacote, instalador, contêiner, manifesto ou canal de release e não faz parte da distribuição da CLI `1.12.0`.
