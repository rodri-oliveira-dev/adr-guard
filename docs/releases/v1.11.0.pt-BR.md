# ADR Guard CLI v1.11.0

[English](https://github.com/rodri-oliveira-dev/adr-guard/blob/v1.11.0/docs/releases/v1.11.0.md)

<!-- release-candidate-only:start -->
A CLI ADR Guard `1.11.0` está preparada no código-fonte, mas **ainda não foi publicada**. A CLI `1.10.0` continua sendo a release pública atual da CLI, dos containers e da GitHub Action. MCP `1.0.1` e VS Code `1.1.1` são candidatas independentes ainda não publicadas. Esta página não comprova atualização em qualquer registry, tag da Action, listagem do Marketplace ou GitHub Release.
<!-- release-candidate-only:end -->

## Principais mudanças

- Adiciona geração MADR 4.0 nativa a `adr-guard new` com templates internos `minimal` e `extended`.
- Seleciona MADR explicitamente com `--adr-format madr-4` ou pela configuração `adr-format` do repositório; a opção explícita mantém precedência e a geração canônica continua sendo o padrão.
- Suporta saída exata e sem efeitos colaterais com `--preview` e `--dry-run`, além das operações `describe`, `preview` e `create` de `new --form` no schema `1.0`.
- Preserva escrita atômica, alocação concorrente segura de IDs, políticas de filename, entradas limitadas e a regra de que documentos gerados são somente rascunhos `proposed` sujeitos à revisão humana.

## Compatibilidade

- Os templates canônicos existentes e seus bytes gerados permanecem inalterados. Templates personalizados continuam exclusivamente canônicos.
- O envelope JSON de `new --form` permanece no schema `1.0`. MADR reutiliza IDs de campos publicados em vez de adicionar campos que clientes estritos existentes poderiam rejeitar.
- Argumentos existentes da CLI, códigos de saída `0`–`4`, schemas de validação, ordenação determinística e aprovação humana de ADRs permanecem compatíveis.
- A seleção do formato MADR vale para toda a operação de validação ou geração; registros canônicos e MADR devem permanecer em diretórios invocados separadamente.
- O runtime continua sendo .NET 10. A geração MADR nativa é offline e não exige MCP nem provider de IA.

## Distribuição preparada por esta release

Depois do merge e de uma execução de CI bem-sucedida para o commit selecionado da `main`, uma pessoa mantenedora autorizada poderá disparar manualmente **Release** com `version=1.11.0`. O workflow valida, compila, testa, empacota, instala e executa smoke tests no build de release antes de poder:

- publicar `RodriOliveira.AdrGuard` `1.11.0` no NuGet.org e no GitHub Packages;
- publicar o mesmo build da CLI para `linux/amd64` e `linux/arm64` no GHCR e no Docker Hub;
- criar a tag exata `v1.11.0`, mover a tag de compatibilidade `v1` somente depois dos gates de publicação e criar a GitHub Release correspondente.

O simples merge desta preparação não publica artefatos nem cria ou move tags.

## Segurança e confiabilidade

- Preview e dry-run não criam ADR, índice, artefato temporário, lock nem reserva de ID.
- A criação renderiza novamente sob o lock existente de alocação entre processos, valida o conteúdo final e promove atomicamente um arquivo temporário sem sobrescrever ADR existente.
- Templates personalizados não podem injetar uma estrutura MADR, e entradas de formato/configuração mantêm parsing estrito e tratamento de paths limitado ao repositório.
- A metadata gerada `status: "proposed"` representa somente estado de rascunho e nunca implica aprovação arquitetural ou conformidade.

## Componentes independentes relacionados

- `AdrGuard.Core` continua interno e não empacotável; não possui versão ou release independente.
- MCP permanece na candidata-fonte `1.0.1`, com artefatos `1.0.0` publicados separadamente e seu workflow independente **MCP Release**.
- VS Code permanece na candidata-fonte `1.1.1`; ela invoca uma CLI compatível instalada separadamente e não é incluída neste pacote.
