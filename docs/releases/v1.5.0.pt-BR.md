# Release candidate do ADR Guard v1.5.0

O ADR Guard 1.5.0 está preparado como a próxima release coordenada de funcionalidade retrocompatível. Ele **não é publicado** por este pull request. Merge, criação de tags, upload de pacotes/imagens, movimentação da tag da Action e criação da GitHub Release continuam operações manuais pós-merge.

## Análise de impacto arquitetural

- `adr-guard impact [repository] --base-ref <ref> --map <arquivo> [--format text|json]` correlaciona alterações Git locais e limitadas com mapeamentos ADR-código explícitos e estritos.
- Os contratos de mapeamento e relatório são versionados independentemente como schema 1.0. Os contratos existentes de JSON/SARIF do `check`, baseline, review e CLI não mudam.
- Evidências de rename e delete preservam paths anteriores. Alterações não mapeadas permanecem visíveis, e decisões não resolvidas/inativas são `unknown`; o comando nunca apresenta achados como vereditos de conformidade.
- Análises bem-sucedidas retornam `0` mesmo quando decisões são afetadas. Uso inválido retorna `2`; falhas de repositório, Git, mapeamento, limites e cancelamento retornam `3`.

## GitHub Action e container

- A Action adiciona os inputs explícitos `impact`, `base-ref` e `impact-map` sem alterar o modo padrão `check` nem as regras de eventos confiáveis do review com provider.
- O modo impact monta o checkout como somente leitura, desabilita rede, não encaminha credenciais do provider/GitHub, valida o contrato da imagem selecionada e renderiza um summary consultivo, escapado e limitado.
- O runtime non-root do container agora inclui Git. Build do container, smoke tests funcionais e scan de vulnerabilidades MEDIUM/HIGH/CRITICAL corrigíveis continuam gates da publicação.

## Compatibilidade e segurança

- O formato canônico do ADR Guard continua padrão. O estudo de caso comprova ADRs canônicos Accepted/Proposed junto com o opt-in de prefixo legado da Fase 0 e o tratamento de ciclo de vida inativo.
- IDs estáveis são únicos, links Markdown comuns não viram mapeamentos, paths ficam contidos no repositório e globs usam um subconjunto limitado sem regex.
- A análise não executa fetch, checkout, inferência do conteúdo-fonte, mutação do filesystem, escrita na API do GitHub, descoberta de secrets ou publicação.

## Estado da distribuição e gate de release

A GitHub Release/tag `v1.4.0` já existe, mas sua distribuição coordenada está incompleta: a tag móvel `v1` da Action ainda resolve para v1.3.0, o NuGet.org termina em 1.3.0 e as imagens 1.4.0 não existem no GHCR e Docker Hub. Essas são falhas preexistentes do estado de release, não regressões da Fase 1. Tags públicas não devem ser movidas ou substituídas de forma avulsa.

Por isso, os jobs atuais de auditoria da distribuição pública e de contrato da Action continuam bloqueados até que um mantenedor autorizado conclua e verifique a recuperação coordenada da v1.4.0. A janela mais segura para a recuperação é antes do merge deste pull request da Fase 1: depois que o baseline do pacote passar para 1.5.0, o workflow protegido rejeitará 1.4.0 por ser inferior ao `VersionPrefix`, e uma recuperação posterior exigirá um caminho separado e revisado. Não contorne os checks nem mova tags manualmente.

A versão 1.5.0 foi selecionada porque esta fase adiciona capacidades retrocompatíveis ao NuGet/CLI e à Action/container, e `v1.4.0` não pode ser reutilizada. Antes da publicação, o mantenedor deve aprovar uma release coordenada a partir do commit exato incorporado à `main`, depois de toda a CI obrigatória passar. O workflow deve publicar/verificar NuGet.org, GitHub Packages, imagens exatas/major no GHCR, imagens exatas/major no Docker Hub, `v1.5.0` imutável, `v1` móvel, asset do pacote e GitHub Release na ordem protegida. Nenhuma publicação ocorreu durante a preparação destas notas.
