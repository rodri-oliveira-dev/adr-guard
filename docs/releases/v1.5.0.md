# ADR Guard v1.5.0 release candidate

ADR Guard 1.5.0 is prepared as the next coordinated backward-compatible feature release. It is **not published** by this pull request. Merging, tagging, package/image upload, Action-tag movement, and GitHub Release creation remain manual post-merge operations.

## Architecture impact analysis

- `adr-guard impact [repository] --base-ref <ref> --map <file> [--format text|json]` correlates bounded local Git changes with strict explicit ADR-to-code mappings.
- Mapping and report contracts are independently versioned as schema 1.0. Existing `check` JSON/SARIF, baseline, review, and CLI contracts are unchanged.
- Rename and deletion evidence preserves previous paths. Unmapped changes remain visible, and unresolved/inactive decisions are `unknown`; the command never presents findings as compliance verdicts.
- Successful analyses return `0` even when decisions are affected. Invalid usage returns `2`; repository, Git, mapping, bounds, and cancellation failures return `3`.

## GitHub Action and container

- The Action adds explicit `impact`, `base-ref`, and `impact-map` inputs without changing the default `check` mode or trusted-event rules for provider-backed review.
- Impact execution mounts the checkout read-only, disables networking, forwards no provider/GitHub credentials, validates the selected image contract, and renders a bounded escaped advisory summary.
- The non-root container runtime now includes Git. Container build, functional smoke tests, and MEDIUM/HIGH/CRITICAL fixed-vulnerability scanning remain publication gates.

## Compatibility and security

- Canonical ADR Guard remains the default format. The case study proves canonical Accepted/Proposed ADRs together with the Phase 0 legacy-prefix opt-in and inactive lifecycle handling.
- Stable IDs are unique, ordinary Markdown links do not become mappings, paths are repository-contained, and globs use a bounded non-regex subset.
- The analysis performs no fetch, checkout, source-content inference, filesystem mutation, GitHub API write, secret discovery, or publication.

## Distribution status and release gate

GitHub Release/tag `v1.4.0` already exists, but its coordinated distribution is incomplete: the moving `v1` Action tag still resolves to v1.3.0, NuGet.org ends at 1.3.0, and 1.4.0 images are absent from GHCR and Docker Hub. These are preexisting release-state failures, not Phase 1 regressions. Public tags must not be moved or replaced ad hoc.

The existing CI public-distribution and Action-contract jobs therefore remain blocked until an authorized maintainer completes and verifies the coordinated v1.4.0 recovery. The safest recovery window is before this Phase 1 pull request is merged: after the package baseline becomes 1.5.0, the protected workflow rejects 1.4.0 as lower than `VersionPrefix`, so a later recovery would require a separately reviewed recovery path. Do not bypass the checks or repoint tags manually.

Version 1.5.0 is selected because this phase adds backward-compatible NuGet/CLI and Action/container capabilities and `v1.4.0` is unavailable for reuse. Before publication, the maintainer must approve a coordinated release from the exact merged `main` commit after all required CI passes. The workflow must publish/verify NuGet.org, GitHub Packages, GHCR exact/major images, Docker Hub exact/major images, immutable `v1.5.0`, moving `v1`, the package asset, and the GitHub Release in its protected order. No publication occurred while preparing these notes.
